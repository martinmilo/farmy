# farmy 0.2.0

A factory agent can now run the profile's tests itself while it works: `farmy-verify` runs them on a snapshot
of its tree and hands back their output and exit code, while only the gate decides. This adds to farmy's
contract (a profile key, a program in the agent's container, record files in the run's folder and three
limits), hence 0.2.0. A profile without `verify` runs as before.

## Factory

- **`verify` in a profile.** It names a command under `commands:` that the agent may run as often as it
  likes. `farmy factory start` refuses a name that is not under `commands:`, naming it, before any run
  container starts. See "On-demand verify" in `docs/factory.md`.
- **`farmy-verify [args…]` for the agent.** Called in the agent's container, it runs that command, each
  argument appended as one word, on a snapshot of the agent's tree as the iteration commit would make it:
  `writes` as they are now, `protects` and `hidden` as the run started them (so a hidden suite runs, though
  the agent cannot read it). The output reaches the agent as it comes and `farmy-verify` exits with the
  command's exit code, adding a last line on stderr for 124 to 127. When the command could not run at all,
  it says `farmy-verify: could not run: <reason>` and exits 125. The agent's prompt says all this, even
  when `factory/prompt.md` omits it.
- **It decides nothing.** The gate tests the iteration's commit as before. A verify is never an iteration,
  and its snapshot is on no branch and never pushed. Calls run one at a time and count toward
  `iteration_timeout`; when the agent's container ends, a running verify is stopped and waiting calls
  never run.
- **Isolation.** Each call runs in a new container made as the gate's test container (the run volume
  read-only, no proxy, no way out), with fresh sidecars of its own, none with `gate: {network: none}`.
  The agent's container gets no farmy binary, Docker socket, broker or network for it: only
  `farmy-verify`, a small `sh` program mounted read-only, and two folders from the run's `verify/` folder.
- **Limits.** Three constants, not settings. Each ends the call as one that could not run (exit 125), with
  its own line:
  - `VERIFY_OUTPUT_CAP`, 4 MiB of the command's stdout and stderr together. Beyond it the verify is
    stopped: `the output exceeded 4 MiB, so the verify was stopped`.
  - `VERIFY_QUEUE_LIMIT`, 4 waiting calls, the running one not counted. A fifth fails at once and is not
    a verify: `the verify queue is full (4 calls are waiting)`.
  - `VERIFY_PREPARE_OUTPUT_CAP`, 64 KiB from the verify container before the command starts. Beyond it
    the verify ends before the command runs: `the verify container printed more than 64 KiB before the
    command started`.

  The gate has none of these limits.

## Run record

- Each call is kept in the run's folder as `iteration-<i>.verify-<k>.log`: header lines, a blank line,
  then everything the command printed. In the header, `args` is a JSON array and `command` and `reason`
  are JSON strings, so no value spans a line; `commit` is the snapshot's id, or `-` when none was made;
  then `started`, `ended` and `exit` (137 for a stopped verify).
- The snapshot's id is taken only as a full commit id, 40 or 64 lowercase hex digits. Anything else is a
  snapshot that failed: `could not run: the snapshot failed: git printed no commit id`, and `commit: -`.
- With `verify` set, `state.json` counts each iteration's verifies (`verifies`), and `farmy factory show`
  appends the count to each iteration's line (`verifies 2`).
