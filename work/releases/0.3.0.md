# farmy 0.3.0

farmy no longer needs a folder of yours: it keeps its configuration in `~/.config/farmy` and its state in
`~/.local/state/farmy`, so the installer, `farmy add` and `farmy` are all it takes to reach a first service. On
Linux with Docker Engine farmy now runs as you instead of root. The control container is never replaced while a
factory run or the session is live in it, and `farmy --version` names the commit a build came from.

## Where farmy keeps things

- **The default home.** Configuration in `$XDG_CONFIG_HOME/farmy`, else `~/.config/farmy`; state (`.work/`) in
  `$XDG_STATE_HOME/farmy`, else `~/.local/state/farmy`; the same paths on a Mac. The first command sets it up: a
  `farmy.yml` with every default, `services/`, and a `.gitignore` that keeps `.env`, `services/*.env`, `.work/`
  and farmy's temporary files out of git. On a terminal it asks once whether to keep the folder in git, unless
  the folder already lies in a Git repository.
- **The folder in use**, first match: `farmy -C <dir>`, `FARMY_DIR`, the nearest folder from the current one up
  that holds a `farmy.yml` (a project folder, with its state in its own `.work/` as before), else the default
  home. Run farmy from any folder.
- **`farmy config path`** prints the folder in use. **`farmy config git`** keeps it in git (`.gitignore`,
  `git init`, a first commit, never a `.env`), so that `git clone` + `farmy` brings your services to another
  machine.
- `farmy status` begins with a `folder` line, `status --json` has `folder`, and the session's header names the
  folder. With no service defined, both say `No services yet: farmy add <git url> [--image …]`. Messages about
  a missing or unknown service name the folder farmy looked in.
- Without `HOME` (as under some service managers), farmy refuses to use the default home and creates nothing.
  The message names `HOME` and the ways out: `XDG_CONFIG_HOME` and `XDG_STATE_HOME`, `FARMY_DIR` or `-C`.
- On a Mac the shim runs git only when the developer tools are installed (`xcode-select -p`), so farmy no
  longer sets off their install prompt.

## First start

- **`farmy init` is optional.** `start`, `restart` and `rebuild` in a folder without `.env` write it the way
  `init` does, without a question, and say so on stderr. The Git identity comes from `GIT_USER_NAME` /
  `GIT_USER_EMAIL`, else from your host's global git configuration. An existing `.env` is left as it is.
  Without a whole Git identity nothing is written and the start is refused as before, naming `.env` and
  `farmy init`.

## Linux: farmy runs as you

- **No more root files.** On Linux with Docker Engine, root in a container is root on the host. So the shim now
  runs every farmy command in the control container as your uid and gid (`docker exec -u`), the session
  included, and everything farmy starts runs as you too: factory and pipeline controllers, git, and the git
  container that fetches build files. Files farmy writes are yours from the moment they are written, and the
  chown after each command is gone. Agent containers keep their own user, `dev` (1001).
- **What you get there.** The control container gets the Docker socket's group. You get a home of your own,
  `/home/farmy/<uid>` in the volume `farmy-home`, so Docker's client config, git's global config and known hosts
  kept there outlive the control container. The holder's socket is `/tmp/farmy-<uid>/hold.sock`.
- **Settled once.** Who farmy runs as is settled when the shim makes the control container and kept in its
  label `farmy.user`. A shell whose group changed (`newgrp docker`) is still you; another user gets a control
  container of their own.
- **Hand-back.** Files an older farmy left root's in farmy's own folders are handed back to you once, when the
  control container is made: the default home's two folders and `.work/` of a project folder of yours. A project
  folder itself and what you keep in it (`farmy.yml`, `services/`, `.env`) are never changed. A root-owned file
  left there stays root's, and the command that fails on it names it.
- **`sudo farmy`** runs farmy as the owner of the folder. In the default home it acts for the user who ran
  `sudo` (`SUDO_UID:SUDO_GID`). A control container made for root is never used for a plain user's commands.
- **Root stays root where that is already you.** On Docker Desktop, on a Mac and with a rootless daemon, farmy
  runs as root as before.

## The control container

- **Live runs keep it.** The shim never replaces the control container while something is live in it: a
  factory run, a pipeline, a factory command waiting with `--wait`, or the session. A command for another folder
  is refused in one line naming the folder the container serves, how many runs are live and `farmy -C <folder>`.
  When the container is due for another version or image, every command is refused naming each run and the
  way out (`farmy factory cancel <id>`, ending the session). `farmy stop` (no name) and `farmy factory cancel
  <id>` still run in it. When Docker cannot say what runs in it, it is kept as if runs were live.
- **Read-only commands run beside it.** For another folder, `status [--json]`, `help`, `config path`,
  `factory list`, `factory show`, `factory log`, `logs`, `egress log` and `tui --version` run in a container of
  their own (`docker run --rm` of the control image), while the other folder's runs go on.
- **One maker at a time.** Two farmy commands started together no longer race to make the control container:
  the second says `another farmy is making or reading the control container; waiting for it` and then reuses
  it. The lock is `control.lock` in the state home; one left by a killed farmy is taken over.
- **Read as a container.** A control container removed by hand (`docker rm -f farmy`) is made anew even when
  the `farmy` network is still there. A read that fails is retried, then the command is refused naming Docker's
  error, and the container is kept. Warnings the docker client prints on stderr no longer count as an answer.

## Build files

- **From the repository only.** A service's Dockerfile and `build_files` come from the committed tree of its
  branch, whether it is cloned over https, ssh or `file://`. `dockerfile:` and each `build_files` entry must be a
  relative path inside the repository (not absolute, no `..`). Any other entry is refused before anything is
  fetched, naming the entry and the service file.
- **Links.** A file committed as a symlink is followed inside the repository and reaches the build as a regular
  file. One that leads out of the repository or to nothing stops the start before anything is built:
  `[shop] build_files: 'Gemfile.lock' points outside the repository (a link to ../.env) …`.
- **Over ssh** the clone runs as root in the git container's own filesystem and hands the files over; farmy
  writes them into `.work/<name>/ctx` as you.

## Versions and updates

- **`farmy --version`** prints `farmy <version> (<short commit>)`: the shim, the binary and `farmy tui
  --version` alike. Control images carry the commit as `farmy.commit`. The build hash is no longer printed.
- **Release candidates.** A version may also be `MAJOR.MINOR.PATCH-rc.N`, in a `farmy.yml` pin, `farmy update
  --to` and the installer's `--to`. Versions are compared as SemVer orders them (`0.3.0-rc.1` < `0.3.0-rc.2` <
  `0.3.0`). A release candidate is published under `next`, never `latest`, so installs and `farmy update` from a
  release stay on releases.
- **From a release candidate, `farmy update` never goes back.** Without `--to` or a pin it goes to the newer of
  `latest` and `next`, and when both are older it refuses and changes nothing: `farmy: 0.4.0-rc.1 is newer than
  the latest release, 0.3.0; use --to 0.3.0 to go back`.

## Upgrading from 0.2.0

1. **Pins.** If a `farmy.yml` pins `farmy: '0.2.0'`, change the pin to `'0.3.0'` first; `farmy update` installs
   the pin.
2. **Update.** Run `farmy update`. The next command replaces the control container once no factory run,
   pipeline or session is live in it; until then it is refused, naming each and how to end it. The new
   container holds no secrets yet, so the next command that loads the brokers obtains them again.
3. **Your containers folder.** farmy 0.2.0 worked in the current folder; 0.3.0 uses the nearest folder with a
   `farmy.yml`, else the default home. A containers folder with a `farmy.yml` keeps working as it is, its state
   still in its `.work/`. In one without, farmy says
   `farmy: using ~/.config/farmy; this folder has no farmy.yml — to keep using it: touch farmy.yml (or farmy -C .)`.
   Run `touch farmy.yml` there, or set `FARMY_DIR` to the folder. farmy never moves or copies your files.
4. **On Linux with Docker Engine**, the new control container hands back the files 0.2.0 left root's in
   `.work/`. What 0.2.0 kept in the control container's own home (`/root`, the volume `farmy-control`), such as
   a `docker login` or SSH known hosts made in it, stays root's and is no longer used: your home there starts
   empty.
5. **Build files.** A definition whose `dockerfile:` or `build_files` names an absolute path or a path with
   `..` is refused now. Commit what the build needs into the repository and name it by its relative path.
6. **App images.** `farmy status` marks app images built by 0.2.0 (`built by 0.2.0, now 0.3.0: farmy rebuild
   <service>`). The toolbox is unchanged since 0.2.0, so the rebuild can wait until it suits you.
7. **Scripts** that read `farmy --version` now get `farmy 0.3.0 (<short commit>)`.

## Known limitations

- Windows with WSL2 and Docker Desktop is unverified. Bind mounts from a WSL distro are believed to keep raw
  uids, and whether farmy can run as you there depends on the socket's group in Docker Desktop's VM. Nothing in
  farmy refuses it; try it, and tell us what you find.
- A Docker daemon that remaps users (`userns-remap`) keeps farmy running as root, and root and every uid in a
  container map to subordinate uids on the host, so farmy cannot write your files as you. Use a daemon without
  remapping, or a rootless one.
- The toolbox's apt path is the supported one; apk remains best effort.
