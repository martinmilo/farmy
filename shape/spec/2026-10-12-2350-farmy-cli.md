# 2026-10-12 23:50 — farmy, the command: one set of containers per repository

The first piece of work. It draws on the owner's brief (kept outside the repository)
and on the program the owner copied into `work/` on 2026-10-12: a per-repository dev-environment
orchestrator from a client project, which he asked to be stripped of every container definition
and of everything client-specific while keeping its ability to boot containers and pull
repositories. This record fixes what that program is, in farmy's terms, so that it can be tested
from outside and grown from here. `FORMATS.md` holds the formats and names in full.

## What was decided

- **farmy is one command, `farmy`, run in the folder that defines the containers.** On the host
  that is the `containers` folder, which exists already and is separate from farmy. The folder
  holds `ports.yml`, `services/<name>.dev.yml`, optional `services/<name>.env` and seed dumps,
  and the machine's own `.env`. farmy keeps its state in `.work/` there. farmy itself ships no
  service definition: a fresh folder has no services, and farmy says so and points at the README
  section "Adding a service".
- **One set of containers per service, named after it:** the app container `<name>`, the
  sidecars `<name>-pg` and `<name>-redis` when the manifest asks for them, and the credentials
  helper `<name>-creds`. One shared container `farmy` (the knowledge MCP) starts with the first
  service and stops with the last. These names are the user's interface (`docker ps`,
  `docker exec hub ...`), so they are promised.
- **Adopted from the brief:** Docker under OrbStack, driven through the docker CLI and compose
  (brief, section 3); every container runs with an init process (§3, the zombie finding in §2); the
  checkout and the database live on named volumes, `<name>-src` and `<name>-pg-data`, never in
  a writable layer (§4): `stop` keeps them, `destroy` removes them; everything is stopped
  unless in use (`stop` with no name stops it all).
- **The forge is configurable and the token stays out of the app container.** `.env` names the
  Git host (`FORGE_URL`, a self-hosted forge or GitHub, over HTTPS; GitHub by default), a token
  (`FORGE_TOKEN`, optionally per owner), and a default owner. The token reaches only
  `<name>-creds`, which proxies Git for the app container. Without a token, public repositories
  still work and farmy says so. A manifest names its repository as `owner/name` on that host, as
  a full URL, or not at all (then `FORGE_OWNER/<name>`).
- **A service runs from an image or from its own Dockerfile.** With `dockerfile:`, farmy reads
  the Dockerfile (and the `build_files` the stage copies) from the repository at the manifest's
  branch and builds the named `target`. A forge that cannot be reached, or a build file that is
  not in the repository, stops the start and says which.
- **Ports come from `ports.yml`:** a block per service; the first port of the block publishes
  the app's first port, the next ones the next. `${url:<service>}` and `${port:<service>}` in a
  manifest's `env:` resolve to that service's host address and port, so one service can be
  pointed at another. `LAN_HOST` in `.env` makes `url` and `status` show the address other
  machines use.
- **Postgres conveniences stay**, since Hub needs them: `create_databases_from` creates the
  databases that env URLs name, `schema_sql` loads a schema file from the checkout into a database
  that was just created, and a `<name>.seed.dump` next to the manifest is restored at the first
  start.
- **The command line:** `init`, `start`, `stop`, `restart`, `rebuild`, `destroy`, `status`,
  `url`, `run`, `logs`, `ssh`, `code`, `help`. Exit 0 done, 1 refused, 2 a mistake in the
  command line. The usage on stdout; refusals and warnings on stderr, naming the file, key,
  repository or command to look at. `destroy` asks on stdin and does nothing unless answered `y`.
  The copied program's old commands (`up`, `down`, `nuke`, `login`, `secrets`, ...) are gone,
  not aliased.
- **What is not configurable through `.env` is not passed on:** a key in `.env` other than the
  Git identity does not reach any container. Per-service environment goes in the manifest's
  `env:` or in `services/<name>.env`.

## Left out of this piece

- The four roles per repository (`dev`, `shape`, `app`, `test`), the test container as the gate,
  and the harness of the Sandcastle notes: later records, once the open questions below have
  answers. This piece is the base they will be built on: one `dev`-style container per
  repository.
- An internal network without egress (brief, section 4, rule 3): open question 5 (dependencies without
  internet) is unanswered, so app containers keep normal network access for now.
- `logs`, `ssh` and `code` are pass-throughs to the container or the editor and are not tested.
- `seed_unless`, and reading database names from env files inside the checkout: only
  `create_databases_from` is promised.
- the shared dev container itself, and moving any existing repository.

## Scenario list

One sentence per test. Test files are under `test/farmy/`.

help_test.rb
- farmy with no arguments prints the usage with every command
- farmy help prints the usage
- an unknown command is refused and farmy help is pointed at
- the copied program's commands up, down, login and secrets are unknown

defining_services_test.rb
- status in a folder without services says that none is defined yet and where to add one
- starting a service when none is defined says so
- a service in ports.yml without a manifest is refused by the name of the missing file
- a manifest without a line in ports.yml is refused by the name of ports.yml
- a service that is not in ports.yml is unknown and the defined ones are named
- a manifest without repo and no FORGE_OWNER in .env is refused by both names
- two services sharing a port block are refused
- status lists every defined service with its port block
- status shows a service that was never started as stopped

init_test.rb
- init writes .env with the name and email the host's Git is configured with
- init leaves an existing .env as it is
- init without Docker running stops at Docker and writes nothing
- init in a folder without services says so and names the README section
- init without a forge token says that only public repositories will clone

start_test.rb
- starting hub runs its container with the first host port of its block on the app port
- a service with several ports gets consecutive host ports of its block
- the sidecars a manifest asks for run next to the app
- every container farmy starts has an init process
- the checkout lives on a volume named after the service
- the forge token reaches only the credentials helper
- a services/<name>.env file reaches that app container
- ${url:hub} in a manifest becomes hub's address on the host
- ${port:hub} in a manifest becomes hub's first host port
- starting notes starts hub first because notes asks for it
- the shared knowledge container starts with the first service
- the databases named in create_databases_from are created in the service's Postgres
- the schema file is loaded into a database that was just created
- a seed dump next to the manifest is restored into the service's Postgres
- starting a service that is already running leaves it running and says so
- starting without Docker running is refused
- starting without .env is refused and init is pointed at
- starting with an .env that lacks the Git identity is refused by key
- starting without a forge token works and says that only public repositories clone
- start without a service name is a mistake in the command line

repository_test.rb
- a manifest names its repository as owner and name on the forge
- a manifest may name its repository by a full clone URL
- a manifest without repo is cloned from FORGE_OWNER and the service name

stop_and_destroy_test.rb
- stopping hub keeps its containers and volumes but nothing of it runs
- stop with no name stops everything, the shared container too
- stopping a service that is not running says so
- destroy answered y removes the containers and volumes and keeps the manifest
- destroy answered n leaves everything as it is
- restart picks up a changed manifest

status_test.rb
- status shows a started service as running with its address
- status marks a service whose manifest changed since it started
- status without Docker running is refused
- url prints the service's address on the host
- url with LAN_HOST in .env prints the address other machines use
- url prints one line per published port
- run executes a command inside the app container
- run on a service that is not running is refused and start is pointed at

build_from_repository_test.rb
- a service with a dockerfile has the named stage built with the files it copies
- the Dockerfile is read from the branch the manifest names
- a forge that cannot be reached stops the start and names the repository and FORGE_URL
- a build file that is not in the repository stops the start and names it
- rebuild builds the image again from the Dockerfile as it is now
