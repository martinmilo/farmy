# Publishing

The owner requested a shaper-and-worker cycle on `farmy-workbench`: record the requirements
and open questions first, confirm scenarios, then write acceptance tests and hand off to the
worker. This record preserves the publishing request while the separately approved toolbox
and pipelines work proceeds. Publishing's questions and scenario list have not yet been
answered or approved; this record authorizes neither a live push nor a release.

Farmy's public source lives in a public Forgejo repository, which pushes a read-only mirror
to GitHub. Development continues in the private repository. The public history contains
release snapshots, never the private development history.

## Requested behavior

1. `FARMY_REGISTRY` defaults to `ghcr.io/<owner>/farmy`. The owner is a build-time constant
   set in one place. An explicit registry override remains available. The installer is a
   GitHub release asset, and the README links its release download URL. Source fallback for
   a local Docker build points to the GitHub mirror's corresponding tag.
2. `.github/workflows/release.yml` is the real tag-release workflow, rather than an example
   that a publisher must copy. A `v*` tag builds control, keys, knowledge and gate images
   natively on `ubuntu-24.04` for Linux amd64 and `ubuntu-24.04-arm` for Linux arm64. Jobs
   push per-architecture digests to GHCR using `GITHUB_TOKEN`, then merge those digests into
   multi-architecture manifests tagged `<version>` and `latest`. The workflow attaches the
   install script and checksums to the GitHub release. Acceptance tests inspect its
   structure, including platforms, tags and `permissions: packages: write`; execution of
   the actual workflow happens on GitHub.
3. `bin/publish <version>` runs from the private repository. It produces the public tree as
   one squashed release commit on top of the previous public commit, with configurable
   author `farmy maintainers <…>`. It runs the tree privacy scan and `bin/scan-history` on
   the resulting public repository, refuses any hit, and pushes only `main` and the release
   tag to the public remote selected by one config line. No private development commit may
   become reachable from any published ref.
4. README and CONTRIBUTING identify GitHub as a read-only mirror and direct issues and
   contributions to configurable destinations. These instructions must agree across the
   Forgejo public tree, GitHub mirror and release documentation.

## Open questions, with proposed defaults

1. **PUB1 — Public tree and layout.** Which source, tests, docs, records and support files
   belong in a public snapshot; does the public repository retain `work/` and `shape/`, or
   put the runtime distribution at its root? What happens to symlinks into excluded paths?

   **Proposed default:** Define an explicit reviewed export allowlist covering runtime
   source, its build inputs, public documentation, licence and approved tests. Exclude
   private configuration, generated state, build products and internal development notes.
   Preserve the selected layout across releases and refuse dangling or escaping symlinks.
   Confirm the actual list and layout before writing tests; the resulting tree must build
   directly from the documented Docker context at a mirror tag.

2. **PUB2 — Configuration and image names.** Where do the owner constant, public Forgejo
   remote, mirror URL, author and contribution text live? Is the requested registry prefix
   followed by the existing `farmy-control`, `farmy-keys`, `farmy-knowledge`, `farmy-gate`
   names, or by shorter role names?

   **Proposed default:** Keep public release identity in one declarative configuration
   source consumed at build time; keep the public destination in a single `public_remote`
   setting used by `bin/publish`. Preserve role names, giving
   `ghcr.io/<owner>/farmy/farmy-control:<version>` and corresponding helper names. Store
   author and contribution text as explicit public values. Keep transport credentials and
   private-repository identities outside the export and out of command output.

3. **PUB3 — Metadata sanitization.** Does the configurable identity cover author only, or
   also committer and annotated-tag tagger? Which commit messages, timestamps and source
   identifiers may appear publicly?

   **Proposed default:** Use the configured `farmy maintainers` identity for author,
   committer and tagger, overriding ambient Git identity. Use a neutral release message
   containing the version, and release timestamps. Copy no private commit messages,
   private SHA references, remote URLs, notes, reflogs or signatures. Preserve required
   licence attribution as public content under the existing narrow copyright exception.

4. **PUB4 — Scan scope and missing denylist.** Must publication refuse when the denylist
   is missing, unreadable or empty? Does the history scan cover tag metadata, paths and
   unchanged historical content as well as commit metadata and diffs?

   **Proposed default:** Publication fails closed for a missing, unreadable or empty
   denylist. Scan the complete staged public tree and all commits and tags reachable from
   the proposed public refs, including author, committer, tagger, messages and paths.
   Retain the existing licence copyright exception only at its defined location. Any hit
   or scanner failure prevents every push. The ordinary suite's documented skip without
   a private denylist remains unchanged; publication has the stricter rule.

5. **PUB5 — First release and trust in the previous public tip.** How is an empty public
   repository bootstrapped, and how are an unexpected public history or changed remote
   tip handled?

   **Proposed default:** The first release is a parentless public commit made only from
   the approved export. Later releases have exactly the fetched public `main` tip as their
   sole parent. Build in an isolated repository containing only public history and exported
   files, with no shared private refs or object alternates. Refuse an unexpected history,
   a scan failure in an old public commit, or a remote-tip race; never force-push over it.

6. **PUB6 — Version and repeat policy.** Does `bin/publish` accept the same stable version
   grammar and VERSION check as `bin/release`; what do dirty input, existing tags, retries
   and older versions mean?

   **Proposed default:** Accept exact stable `MAJOR.MINOR.PATCH`, require it to equal
   `VERSION`, and publish tag `v<version>`. Export a committed private revision and refuse
   dirty tracked input. Refuse a version older than the latest public release and never
   move an existing tag. An already-published matching release is an explicit successful
   no-op; a different tree or metadata under that version is refused. A failed push is
   retryable without making a second public release commit.

7. **PUB7 — Ref atomicity and failure reporting.** Must `main` and its tag advance together,
   and what if the remote does not support atomic pushes? What does the command report if
   Forgejo accepts the push but its GitHub mirror or release workflow later fails?

   **Proposed default:** Use one atomic push of precisely `main` and the new tag, with the
   previously fetched public tip as the expected value. Refuse unsupported atomic pushes
   rather than falling back to a partial publication. Report Forgejo publication separately
   from GitHub mirror synchronization and CI; command success makes no claim that external
   mirroring or image publication finished. Mirror retries never rewrite public history.

8. **PUB8 — Mirror trigger and permissions.** Who configures Forgejo's push mirror, which
   refs are mirrored, and which GitHub credential triggers the tag workflow? Is release
   creation allowed through the workflow's token?

   **Proposed default:** Document an externally configured Forgejo mirror that transfers
   public `main` and release tags using a GitHub identity permitted to update workflow
   files and trigger tag workflows. `bin/publish` knows only the public Forgejo destination.
   Build jobs receive `contents: read` and `packages: write`; the release-assets job receives
   `contents: write`, with only the permissions it needs. Mirror credentials are never part
   of the public tree or acceptance fixtures. Validate actual hosting behavior on GitHub
   when the owner performs the first live release.

9. **PUB9 — Assets, checksums and failed CI.** What are the exact installer/checksum asset
   names and checksum algorithm; must both architectures of all four images succeed
   before manifests, `latest` and release assets are published?

   **Proposed default:** Publish assets `install` and `SHA256SUMS`, using SHA-256 for the
   exact attached installer bytes. The README offers a versioned release-asset URL and
   may also give GitHub's latest-release asset URL. Merge jobs consume all eight produced
   image digests and publish a version manifest and `latest` for each role only after all
   native builds succeed. Release creation and asset upload require those merges to
   succeed. Do not claim cross-image registry updates are transactional if a later push
   fails; report the failed job and permit a release retry.

10. **PUB10 — Issues and contributions.** Should contributions go to public Forgejo pull
    requests, its issue tracker, email, or another intake, and how do accepted changes reach
    the private development repository?

    **Proposed default:** Use configurable public Forgejo issue and contribution URLs in
    README and CONTRIBUTING, identify GitHub as read-only in both, and explain that
    maintainers apply accepted changes in the private development repository. Confirm the
    actual public text and destinations before publication; fixtures use example.com.

## Proposed scenario list — not yet approved

1. **PUBS1.** With no FARMY_REGISTRY override, installer, shim, update and release select the
   configured owner's GHCR namespace from the single build-time source.
2. **PUBS2.** An explicit FARMY_REGISTRY override selects that registry consistently for all
   four image roles without rewriting the public default.
3. **PUBS3.** The README's installer link names the GitHub mirror's release asset and the
   documented checksum verification checks the exact installer bytes.
4. **PUBS4.** A standalone local-build fallback uses the GitHub mirror's matching tag and
   the public tree's build context without requiring a private checkout.
5. **PUBS5.** The real release workflow runs on v* tags and builds all four image roles on
   native ubuntu-24.04 amd64 and ubuntu-24.04-arm runners.
6. **PUBS6.** The workflow authenticates GHCR pushes with GITHUB_TOKEN and grants packages
   write only where required, plus the content permissions needed for release assets.
7. **PUBS7.** Manifest jobs consume both architecture digests for every role and publish
   version and latest tags only after all required native builds succeed.
8. **PUBS8.** A successful release workflow attaches the installer and its checksum asset
   after image publication, while a failed build or merge prevents release success.
9. **PUBS9.** The first local publish creates exactly one parentless public release commit
   from the agreed export and exposes no private development commit through published refs.
10. **PUBS10.** A later local publish creates one new commit whose sole parent is the
    previous public tip, even when many private development commits occurred meanwhile.
11. **PUBS11.** Export includes the agreed buildable public source and excludes private
    configuration, generated state and every path outside the export contract.
12. **PUBS12.** Public author, committer, tagger and messages follow configured public
    metadata and contain no copied private Git identity or development message.
13. **PUBS13.** A privacy hit in the proposed public tree refuses publication with a useful
    location and leaves remote main and tags unchanged.
14. **PUBS14.** A privacy hit in an earlier reachable public commit or tag refuses the new
    publication even when the latest exported tree no longer contains the term.
15. **PUBS15.** A missing, unreadable or empty required denylist or a failing scanner refuses
    publication before any public ref is pushed under the agreed scan policy.
16. **PUBS16.** Invalid or mismatched versions and dirty tracked input are refused with the
    specific cause and no change to public refs.
17. **PUBS17.** Repeating an already-published identical release is a no-op, while a
    conflicting existing version or tag is refused without moving it.
18. **PUBS18.** A remote-tip race or unsupported atomic push leaves main and the release tag
    unchanged and reports why the proposed release was not published.
19. **PUBS19.** Publication pushes only the selected public remote's main and release tag,
    never private branches, notes or other refs, and preserves the private checkout.
20. **PUBS20.** A failed push can be retried without duplicate release commits or a claim
    that GitHub mirroring or image CI succeeded.
21. **PUBS21.** README and CONTRIBUTING both identify the GitHub mirror and render the
    configured issue and contribution destinations consistently.

Publishing tests will use temporary private and public Git repositories, a controlled
denylist, and observable refs and object reachability. Workflow tests read the workflow as
the shipped product. They do not invoke GitHub, GHCR, Forgejo or a live mirror. The real
native workflow run remains a separately reported GitHub validation, not a fake-suite pass.

## Existing contracts that will change

The distribution records dated 09:10 and 09:20 deliberately left the registry unset and CI
as an example. This request replaces those choices with a public default and an executable
release workflow. `ReleaseTest` currently expects a missing FARMY_REGISTRY to be refused;
that expectation must change after this scenario list is confirmed. Explicit registry
overrides, exact VERSION validation, multi-architecture output and host-tool independence
remain part of the distribution contract.

The privacy record at 03:00 permits ordinary tests to skip when a stranger lacks the private
denylist. Publishing's missing-denylist behavior is separately open in PUB4; no existing
privacy test changes until that decision is confirmed. The existing history scan is an
input to the publishing requirement, not evidence that a proposed release passed it.

## Worker handoff after scenario approval

First resolve PUB1–PUB10 and confirm or amend PUBS1–PUBS21. Then add acceptance tests and
record the agreed configuration keys, exported layout, image names, ref rules, metadata,
version grammar, scan failure policy and asset names in FORMATS.md. The shaper will report
new failures and any changed existing test meanings before the worker begins implementation.
The worker receives those contracts and executable test output, not this spec's contents.
No live remote setup, push, mirror creation, registry write or GitHub release is included in
the record-and-test phase.
