# A default home: farmy with no setup

The owner, 2026-10-29: farmy should work with no setup, the way nvim does. There is a default home, and a
containers folder only for those who want one. Six points were given (below, "Decided"). Four forks were
settled in conversation the same day. A read-only work-side helper described today's behaviour; it never
looked into this folder, and its answers shaped the decisions marked *(helper)*.

## What farmy does today *(helper)*

- **The folder.** The binary uses its current directory and nothing else: `farmy.yml`, `.env`, `services/` and
  `.work/` are all relative paths. It does not search parent folders, has no global option and reads no folder
  variable. The shim mounts `$PWD` at the same path in the control container and runs every `docker exec`
  with `-w $PWD`. It replaces the control container when no mount has `$PWD` as its destination. It reads
  the `farmy:` pin, `format:` and `.env`'s `FARMY_UNLOCK_COMMAND` / `FARMY_SECRET_PREFIX` from `$PWD`.
- **Init and farmy.yml.** `farmy.yml` is optional. `init` writes one only on a terminal when agents are chosen.
  Without a terminal it writes none, so a folder that `farmy init` prepared often holds only `.env` and
  `services/`, and so does the test suite's `workshop` fixture.
- **What the folder holds.** Nothing farmy writes into the folder holds a secret except `.env` (a Git identity
  by design) and `services/<name>.env` (the user's own). The latter is copied to `.work/<name>/app.env`.
  `farmy lock`, the holder and the keys broker write nothing to disk, and there is no cache outside `.work/`.
  `tools.lock` lives at the folder's root. Nothing writes a `.gitignore` or runs `git init`.
- **Questions and messages.** Line questions are asked only when stdin is a terminal. The shim passes the
  host's Git identity to `init` only. Four messages say there are no services (`status`, `init`, `start` /
  `restart` / `rebuild` / `url` with none defined, and an unknown service), and none of them names a folder.
  The TUI's header shows "farmy — one set of containers per repository" and the time, and no folder.

## Decided (the owner)

1. **Default locations, XDG with the usual fallbacks.** Configuration lives in `$XDG_CONFIG_HOME/farmy`, else
   `~/.config/farmy`: `farmy.yml`, `services/*.yml` and `.env`. State lives in `$XDG_STATE_HOME/farmy`, else
   `~/.local/state/farmy`, and holds `.work/` (run records, locks, logs). macOS uses the same paths, never
   `~/Library`, so a user can `cat` them. Any command that needs them creates them on first use. `farmy init`
   becomes optional and keeps doing what it does today, in whichever folder it is told.
2. **Resolution order, every command:**
   1. the `-C <dir>` flag;
   2. `FARMY_DIR`;
   3. a `farmy.yml` in the current folder or a parent (project-local setups keep working as now, with `.work/`
      beside their `farmy.yml`);
   4. the default home.

   `farmy status` and the TUI header show which folder is in use.
3. **Fresh machine, no services.** Bare `farmy` opens the TUI with an empty list and one line:
   `No services yet: farmy add <git url> [--image …]`. `farmy add` writes to the resolved folder's `services/`.
   Nothing prints "no service" without saying where it looked.
4. **Migration.** If the default home does not exist and a command runs in a folder with a `farmy.yml`,
   nothing changes for that user. Nothing is copied or moved automatically. `farmy init` in an existing folder
   stays as it is.
5. **Tests and README.** Tests for the resolution order and the empty-state message. The README shows three
   lines: install, `farmy add …`, `farmy`, with no mkdir and no cd. A short section "Where farmy keeps things"
   names the two paths and the project-local alternative.
6. **The config home is meant to be versioned**, like a dotfiles repository.
   - When farmy creates it, it always writes a `.gitignore` there (`.env`, anything the keys broker or
     `farmy lock` writes, caches), so a `git init` can never commit a secret. `.work/` lives under state, so it
     is out by construction.
   - The first time the folder is created on an interactive terminal, farmy asks once: "Keep ~/.config/farmy
     in git? [y/N]". Yes runs `git init` and a first commit of `farmy.yml` and `services/`. No is remembered
     in a marker file and never asked again. Non-interactive runs skip the question.
   - `farmy config git` does the same later, for anyone who said no. `farmy config path` prints the folder.
   - The README section gets one line: track this folder in git and you can bring your services to another
     machine with `git clone` + `farmy`.

   Every existing command keeps its behaviour otherwise.

## Settled in conversation (the owner chose each)

- **Folders without a farmy.yml.** `farmy.yml` stays the only mark of a project folder, as briefed. Two things
  close the gap:
  - `farmy init` writes a `farmy.yml` (all defaults) into a folder that has none, so a folder it prepared is
    found by the next command.
  - When farmy falls back to the default home from a current folder that looks like an old containers folder
    (`services/` with a definition in it, or a `.env` naming `GIT_USER_NAME`, and no `farmy.yml`), stderr
    says which folder farmy uses and how to keep this one: `touch farmy.yml`, or `farmy -C .`. That folder
    is never written to.
- **`farmy init` follows the resolution order.** In a plain folder it prepares the default home. To prepare
  another folder, use `farmy -C ~/containers init`. Running init in `~` can never leave a `~/farmy.yml` that
  every folder below would then find.
- **State path.** `~/.local/state/farmy/.work/`, literally. Every documented path stays
  `<state>/.work/<name>/runs/<id>/`, the same layout a project folder has beside its `farmy.yml`.
- **Scope of this session:** shape, build with a fresh worker, run the full suite alone, merge on green. No
  publish.

## Chosen here (the owner may overrule any of these)

**Resolving the folder**

- **`-C` and `FARMY_DIR` name the folder itself, used as is.** Neither searches upward, and neither needs a
  `farmy.yml` in the folder. That is also the way to keep using an old folder without one. A relative value
  is taken from the current folder. A folder that does not exist is refused, and nothing is created:
  - `-C` gives exit 2, a mistake in the command line, naming the path;
  - `FARMY_DIR` gives exit 1, naming `FARMY_DIR` and the path.
- **`-C` placement.** It comes before the command (`farmy -C <dir> status`), as with git and make. `-C`
  without a value is a mistake in the command line.
- **XDG values.** An empty or relative `XDG_CONFIG_HOME` / `XDG_STATE_HOME` counts as unset, as the XDG spec
  says.
- **The default home's config folder is the default home however it is reached:** `-C`, `FARMY_DIR`, or a
  current folder inside it (it has a `farmy.yml`). Its state stays in the state folder. `.work/` must never
  appear in the folder meant for git.
- **`help`, `--version` and `tui --version` resolve nothing.**

**Setting up the default home**

- **When.** "Created" means *set up*. farmy sets up the default home when its config folder has no
  `farmy.yml`. This happens in any command except `help`, `--version` and `tui --version`. The shim has to
  create the folders before it mounts them, because Docker would create a missing bind source as root, so
  "the folder did not exist" cannot be the test.
- **What set-up does.** It creates the folder, `services/` and a `farmy.yml` with every default (a comment and
  `format: 1`, no pin). It writes the `.gitignore` when there is none and never overwrites one. On a terminal
  it asks the question.
- **A folder that already has a `farmy.yml` is never set up.** That covers a `git clone` from another machine:
  it is used as it is, with nothing asked and nothing written.
- **The question.** It is asked when stdin is a terminal (the binary's rule for questions today) and the folder
  is not already inside a Git repository. A user whose `~/.config` is a dotfiles repository is not asked.
  - "y" or "yes" makes the repository and its first commit.
  - Anything else, an empty answer included, is a no. farmy remembers it in its own state
    (`<state>/.work/config-git-declined`; nothing in it is promised).
  - A set-up without a terminal asks nothing and records nothing. The folder then has its `farmy.yml`, so it is
    not set up again: from then on only `farmy config git` makes the repository. This follows "the first time
    the folder is created".
- **The first commit.** It holds `.gitignore`, `farmy.yml` and whatever `services/` holds then (`.gitignore`
  is added to the brief's list, so a clone carries it). The question comes when set-up happens, before the
  command does its own work. The first `farmy add` on a fresh machine therefore leaves its new definition
  uncommitted. Committing later changes is the user's business, and the yes message says how. The commit's
  identity comes from, in order:
  1. `GIT_USER_NAME` / `GIT_USER_EMAIL` in farmy's environment (the shim now passes the host's to every
     command, not only `init`);
  2. `.env`;
  3. git's own configuration.

  When none of these gives an identity, the repository is made and farmy says the commit needs an identity.
- **The `.gitignore`.** Its lines are `.env`, `services/*.env` and `.work/`, under a comment. `services/*.env` is
  there because those files are the user's own environment and may hold secrets. `.work/` is there in case
  farmy's state ever lands in that folder, for example from an older farmy run there. The keys broker,
  `farmy lock` and caches write nothing to the folder *(helper)*, so they need no line.

**`farmy config`**

- **`farmy config path`** prints the absolute path of the folder in use, one line, for scripts.
- **`farmy config git`** works on the folder in use, the default home or a project folder:
  - it writes the `.gitignore` when there is none, runs `git init` and makes the first commit;
  - a folder already inside a Git repository (its own or a parent's) gets nothing new, and farmy names that
    repository, exit 0;
  - `farmy config` alone, or with another word, is a mistake in the command line (exit 2).

**What the user sees**

- **Paths in messages.** A path under the user's home is written `~/…`, so the question reads as briefed;
  any other path is absolute. `config path` and `status --json` always give absolute paths. Inside the control
  container `HOME` is not the user's, so the shim passes the host's as `FARMY_HOST_HOME`.
- **Status.** `farmy status` prints `folder` as its first line, in the same column as `ports`:
  `folder       <path>`. For the default home it adds `(state in <state path>)`.
  - `status --json` gains `"folder": {"path": …, "state": …}`, both absolute.
  - The TUI's header shows the folder as status prints it.
  - With no service defined, status (stdout, exit 0) and the TUI's empty list print the line
    `No services yet: farmy add <git url> [--image …]`.
  - Every message about no service or an unknown service names the folder farmy looked in.
  - Status's line used to be "no services defined yet … (README → Adding a service)"; the brief's line now
    replaces it. The messages of `init`, `start` and an unknown service keep their wording and gain the folder.
- **Usage.** It shows `-C <dir>` on its first line and lists `config path` and `config git` among the commands.
  `-C` stays out of the COMMANDS list, which the README test reads as command names.

**The shim**

- It resolves the folder on the host in the same order, since the control container can see neither the
  current folder's parents nor the host's `HOME`.
- It creates the folder, plus the state folder when the default home is in use, before it mounts them. It
  mounts each at its own path.
- It reads the pin, `format:` and `.env` from the resolved folder.
- It consumes `-C` itself. On every `docker exec` it passes:
  - `-w <folder>`;
  - `FARMY_DIR=<folder>`;
  - `XDG_CONFIG_HOME` and `XDG_STATE_HOME`, resolved to absolute host paths;
  - `FARMY_HOST_HOME`;
  - the host's Git identity.

  The binary inside then reaches the same answer. A different set of mounts replaces the control container,
  as a different folder does today. The shim-keeps-live-runs branch, not merged, is about runs living in a
  replaced container.
- **macOS.** On macOS the shim uses the same `~/.config` and `~/.local/state`, never `~/Library`. The binary
  always runs in the Linux control container, so on a Mac only the shim decides these paths, and a fake
  `uname` stands in for the Mac in its test.

## How the tests play it

- **The kit.** Every farmy and shim call now runs with:
  - `HOME` set to a folder of the test's own (`<scratch>/home`), so no test can reach the real `~/.config`;
  - `XDG_CONFIG_HOME` and `XDG_STATE_HOME` unset;
  - `DOCKER_CONFIG` kept on the real `~/.docker`, for real-Docker runs;
  - `FARMY_DIR` set to the test's folder.

  Every existing test therefore keeps its meaning: the test's folder is the containers folder.
- **Tests that play a user's machine** (`on_a_fresh_machine`) drop `FARMY_DIR`, so farmy resolves its folder as
  on a real machine. Their files are named as a user would name them: `"~/.config/farmy/services/shop.yml"`,
  with `~` meaning the test's home.
- **Other folders.** `folder_named` gives the test's folder a parent of its own. That parent plays "a folder
  above" for the upward search. It also plays `$XDG_CONFIG_HOME` when the test's folder must be the default
  home's config folder.
- **A terminal** is a pseudo-terminal on stdin (`farmy_on_a_terminal … typing: "y"`). stdout and stderr stay
  pipes, as they are when the shim runs farmy with a terminal attached.
- **The `.gitignore`** is checked by asking git (`git check-ignore`) in a throwaway copy, not by reading lines.

## Existing tests that changed

- `InitTest` "init without a terminal turns no agent on, writes no farmy.yml, and says how to turn one on"
  becomes "init without a terminal turns no agent on: the farmy.yml it writes turns none on, and it says how to
  turn one on".
- `DefiningServicesTest` "status in a folder without services says that none is defined yet and where to add
  one" becomes "status in a folder without services names the folder and says: No services yet: farmy add <git
  url> [--image …]".
- The kit's environment changed for every test, as above. The real-Docker tests (`IntegrationTest`,
  `AgentCliIntegrationTest`) now run the shim through `real_shim`, which gets the same environment. `shim` passes
  the host's git configuration (`host_git_identity`) as `farmy` already did. `ReadmeTest` now also requires
  `farmy config` in the README, since the usage lists it. The `assert_binds_within_workspace` rule now reads
  "the folder or the state folder". The two are the same folder in every existing test.

## Scenario list

Resolving the folder (`default_home_test.rb`, `folder_resolution_test.rb`):
1. On a fresh machine, `add` writes the definition into `~/.config/farmy/services` and nothing into the current
   folder.
2. With `XDG_CONFIG_HOME` set, `add` writes into `$XDG_CONFIG_HOME/farmy/services`.
3. An empty `XDG_CONFIG_HOME` counts as unset: the definition goes to `~/.config/farmy`.
4. Starting a service from the default home keeps farmy's state in `~/.local/state/farmy/.work` and none in
   `~/.config/farmy`.
5. With `XDG_STATE_HOME` set, the state goes to `$XDG_STATE_HOME/farmy/.work`.
6. A `farmy.yml` in the current folder makes it the folder: start keeps `.work/` beside it, and no default home
   is created.
7. From a subfolder, farmy uses the folder above that holds `farmy.yml`.
8. `FARMY_DIR` wins over a `farmy.yml` in the current folder.
9. `-C` wins over `FARMY_DIR`.
10. `-C` names a folder that has no `farmy.yml`, and farmy uses it as it is.
11. `-C` naming a folder that does not exist is a mistake in the command line, naming it, and nothing is
    created.
12. `FARMY_DIR` naming a folder that does not exist is refused, naming `FARMY_DIR`, and nothing is created.
13. Inside the default home's config folder, the state still goes to the state folder, never beside
    `farmy.yml`.
14. A current folder with `services/` and `.env` but no `farmy.yml` is left untouched. farmy says it uses
    `~/.config/farmy` and how to keep this folder (`touch farmy.yml`, `farmy -C .`).

Where it looked, and the empty state:

15. On a fresh machine, status names `~/.config/farmy` as the folder and its state folder.
16. `status --json` gives the folder and the state folder as absolute paths.
17. On a fresh machine, status says "No services yet: farmy add <git url> [--image …]".
18. Starting a service on a fresh machine says no services are defined yet in `~/.config/farmy`.
19. An unknown service is refused naming the folder farmy looked in.

`farmy init`:

20. On a fresh machine, init prepares the default home (its `.env`) and names it.
21. `farmy -C . init` in a plain folder writes a `farmy.yml` there, so the next command run there finds that
    folder.
22. init leaves an existing `farmy.yml` as it is.

The config home in git (`config_home_test.rb`):

23. Setting up the default home writes a `.gitignore` that keeps `.env`, a service's `.env` and `.work/` out of
    git, and keeps `farmy.yml`, definitions and `tools.lock` in.
24. On a terminal, setting up the default home asks "Keep ~/.config/farmy in git? [y/N]". Yes makes a repository
    whose first commit holds `.gitignore` and `farmy.yml`.
25. Answering no makes no repository, and the question is not asked again, even when the folder is set up afresh.
26. Without a terminal, nothing is asked and no repository is made.
27. A default home that already has a `farmy.yml`, as a `git clone` brings it, is used as it is: nothing is
    asked and nothing is written into it.
28. After a no, `farmy config git` makes the repository: its first commit holds `.gitignore`, `farmy.yml` and the
    definitions, and never `.env`.
29. `farmy config git` twice leaves one repository with one commit.
30. `farmy config git` in a folder already inside a Git repository makes none and names that repository.
31. `farmy config path` prints the folder in use.
32. The usage shows `-C <dir>` and lists `config path` and `config git`.

The shim (`shim_folders_test.rb`):

33. On a fresh machine the shim creates `~/.config/farmy` and `~/.local/state/farmy` and mounts both into the
    control container at their own paths.
34. On a macOS host the shim uses the same two folders and nothing under `~/Library`.
35. From a subfolder of a project folder, the shim mounts the folder above that holds `farmy.yml` and runs farmy
    there.
36. `-C` through the shim mounts the named folder and runs farmy there.
37. The shim hands farmy in the control container the folder it resolved, the XDG folders and the host's home.
38. The shim passes the host's Git identity to every command, not only `init`.

Docs (`readme_default_home_test.rb`):

39. The README's first service is three lines, the installer, `farmy add` and `farmy`, and no command in it makes
    or enters a containers folder.
40. The README's "Where farmy keeps things" names both default paths, the project folder found by `farmy.yml`,
    `-C` and `FARMY_DIR`, and that `git clone` + `farmy` brings the services to another machine.
41. Getting started says where farmy keeps things (`~/.config/farmy`) and has the reader make no containers folder.

## Not tested

These are stated in FORMATS.md as contracts:
- macOS for the binary. The binary runs in the Linux control container, so only the shim test covers macOS.
- The TUI's header and its empty-list line. The TUI is not under the suite; both are what status prints.
- The pin, `format:` and `.env` keys the shim reads from the resolved folder rather than `$PWD`.
- The commit's identity. The kit gives every program a fixed Git identity, so a test cannot show where the
  identity came from.
- A relative `XDG_*` value counting as unset, `-C` without a value, and `config` with an unknown word.

## Left out

- **Moving an existing containers folder into the default home.** The owner said nothing moves automatically.
  There is no `farmy config migrate`.
- **More than one default home, or profiles.**
- **Committing later changes for the user.** farmy commits once, at set-up or on `config git`.
