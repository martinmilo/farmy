# Shipping 0.3.0

The owner, 2026-10-30: release 0.3.0 the usual way, now that the pre-release works on their Mac. The pre-release is
not published. Publishing it would have needed a registry login by hand, because the release workflow publishes
stable versions only (record 2026-10-29-1800).

## The check on the owner's Mac (Docker Desktop), 2026-10-30

The build was 0.3.0-rc.1 at d5b1521, from a checkout with no install. All of these held:
- `farmy --version` printed `farmy 0.3.0-rc.1 (d5b1521)`.
- `FARMY_BUILD=1 farmy init` built the control image, labelled `farmy.commit` d5b1521. That was the first real build of
  the Dockerfile's `FARMY_COMMIT` argument.
  - It set up the default home `~/.config/farmy`, with its state folder, and asked the Git question once.
- `status` from the home folder named the default home and `No services yet`, and asked nothing again.
  - Without `FARMY_BUILD` it tried the registry first and built locally when that failed, as the contract says.
- `farmy -C <the owner's containers folder> status` listed that folder's services.
- The installed 0.2.0 took its control container back afterwards.

Not covered by that check:
- the release image build (`release.Dockerfile`), and the narrowed keys, knowledge and gate contexts.
  - CI's 0.3.0 build is their first real build. `bin/release 0.3.0 --image <role> --output <archive>` builds them on a
    machine without pushing.
- build files fetched from a real Git server.
- the three real-Docker integration tests that need a root runner on Linux.

## Decided

- `Distribution::SHIPPED` is `0.3.0`.
- At a release `VERSION` is that release; between releases it is the next release's pre-release. FORMATS.md says so.
- A newer release must be one after 0.3.0: tests that had `0.3.0` for it use `0.4.0`. Those that also need a still
  later release as latest use `0.5.0` where they had `0.4.0`. A newer pre-release is `0.4.0-rc.2` where it was
  `0.3.0-rc.2`. Nothing else in these tests changes.
- Updating from a pre-release (record 2026-10-29-1931) can only be seen in a pre-release build. The four tests for it
  skip while `SHIPPED` is stable, with the reason `needs a pre-release build: this checkout ships 0.3.0, a stable
  release`. They run again once `VERSION` is the next pre-release.
  - Their literals move then: the newer pre-release and newer release to one after that pre-release; 0.2.0 can stay
    the older release.
- Three test names that said "the last release" or "this pre-release" now say "an earlier release" and "this
  version", because 0.2.0 is no longer the last release.

## Tests altered

Each change is to the version or the name only; what each test checks is unchanged.

DistributionTest:
- a mismatched folder pin refuses the binary before any service starts and names the fix
- a quoted folder pin mismatch is refused by the shim before control starts
- version remains available while the folder pin mismatches
- a toolbox built by 0.2.0, an earlier release, is marked older than the shipped 0.3.0 (renamed)
- a toolbox built by 0.4.0-rc.2 / 0.4.0 is not marked older than the shipped 0.3.0 (was 0.3.0-rc.2 / 0.3.0)
- a shim older than the running control image warns with both versions and update (`newer_running_control`)
- farmy.yml and services/shop.yml: format 2 refuses before start and names a published version that reads it
- latest metadata that still cannot read the requested format does not invent a capable version

InstallationTest:
- installation without a version resolves the stable latest control label
- an unpinned update pulls every newest release image and replaces the installed shim
- an explicit update target overrides latest and fixes an existing folder mismatch (0.4.0 pinned, 0.5.0 latest)
- an update target may be a pre-release: farmy update --to 0.4.0-rc.2 installs that pre-release (renamed)
- update without a target respects an exact folder pin instead of latest (0.4.0 pinned, 0.5.0 latest)
- a failed helper-image update preserves the installed shim and all running containers
- a failed shim extraction preserves the installed executable
- the four "from a pre-release" tests skip at a stable release, as above

ReleaseInstallerTest:
- the release's installer, run without --to, installs the release it came from even when a newer one is latest
- the release's installer with --to installs that version

ReleaseTest:
- release version 0.4.0 is refused because it is invalid or differs from repository VERSION (was 0.3.0, which is
  now the repository's VERSION)

PublishingDefaultsTest:
- update without a registry override obtains all four roles from the configured GHCR namespace

ShimLiveRunsTest:
- a control container that runs farmy 0.2.0, an earlier release, is replaced by one of this version when no run is
  live in it, as one of another version is (renamed)
