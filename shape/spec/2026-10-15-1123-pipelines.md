# Pipelines

Recorded on `farmy-workbench`, for the shaper and the worker. The order is this record with open
questions and scenarios, acceptance tests through the fake, then the worker's implementation, in
separate commits. The scenario list and open contracts come back to the owner before tests fix their
meaning. This extends the shaper-and-worker records with automatic sequencing and human review.

A pipeline chains named factory profiles. Draft publication makes work available for review as soon
as its gate passes. Approval identifies an exact commit, and a downstream worker can use reviewed
tests without adopting later branch changes or unreviewed answers that alter those tests.

## Open questions

1. **Configuration and identity.** Pipelines are a sibling of `factory` in the service definition.
   Settle where the per-pipeline handoff limit is written and the exact scope of `factory.concurrency`.
   Named profiles currently occupy every key under `factory`, so a concurrency setting must be
   distinguished from a profile and remain compatible with legacy factory blocks. Define pipeline
   IDs, their relationship to run IDs, and the public status/list/show fields and commands.
2. **Controller lifecycle.** Does pipeline start support `--wait` like factory start, and which exit
   codes describe review, question and terminal failure? Settle resumption after approval, revision,
   interruption or process restart and how cancellation/pruning acts on the parent and child runs.
   Repeating an approval or reading status must not launch the next step twice.
3. **Review and revisions.** Approval pins the gated commit; should it retain today's refusal if the
   branch has moved before approval? The proposed rule retains that check, then uses the recorded
   approved commit even if the branch moves afterward. Does revise create a new run ID on the same
   branch, or append a review attempt to the existing ID, and which states accept it? Preserve the
   history of gated and approved commits; a revision needs fresh approval. Does `--from` still accept
   an unrelated branch with no recorded run, or must every source now have recorded approval?
4. **Drafts and links.** A pushed branch with `awaiting_review` and a compare link is sufficient for the
   requested draft; no forge API to create a pull request is specified. Settle the comparison base,
   URL escaping, web URLs for SSH remotes, and how self-hosted GitLab and Forgejo/Gitea hosts declare
   their forge type. Unknown hosts fall back to the branch name. Retain the existing no-remote
   workbench exception, and define the state and retry behavior when a draft push fails.
5. **Question source and answers.** Fix the shaper's source commit and how approved permitted changes
   return to a worker while preserving its work from before the question. A text-only answer needs
   no changed test and cannot satisfy ordinary red_first; define its distinct answer completion,
   including empty answers, out-of-scope edits and a shaper that asks another question. Decide the
   handling of `.farmy/answer.md` as an out-of-writes, non-committed control file, like question.md.
6. **Handoff counting.** The default limit is three per pipeline. The proposed count is one per worker
   question sent to `on_question`, with the fourth handoff refused before another shaper starts;
   returning its answer does not add another count. Confirm counting across revisions, retries and
   resumed processes, and the behavior when no `on_question` profile is configured.
7. **Meaningful red.** Where is `red_pattern` written for scalar versus mapping gates, what regex
   syntax is supported, and does it match combined stdout/stderr? Settle invalid-pattern validation
   and how crash/execution failure is distinguished from an assertion failure even if earlier output
   happened to match. Omitting the optional pattern keeps existing red_first behavior.
8. **Concurrency and sidecar lifetime.** When the service's slots are full, queue or refuse? Do review
   and question waits release their slots? Runs need distinct Compose projects and data, but settle
   whether sidecars/data reset between gate iterations or live for the run. Define how fixed container
   names, external volumes, bind-backed data, dependencies and health checks are handled so they cannot
   reconnect runs to shared mutable databases. `gate.network: none` must still create no sidecars.
9. **Notifications.** Fix the `notify` YAML shape, format selection, payload fields, authentication,
   timeouts/retries and duplicate handling for ntfy, Slack-compatible and plain JSON destinations.
   Define which failure results emit events and whether failed delivery is diagnostic only; the
   proposed policy does not change an already recorded gate or approval result.
10. **Egress compatibility.** Confirm retaining `false` as an alias for `off` as well as the requested
    `true` alias for `enforce`, and whether public JSON mode names change from strict/unrestricted.
    Preserve strongest-policy precedence and factory enforcement. The protocol documentation should
    say other protocols have no independent outward route: CONNECT is an opaque TCP tunnel, not
    application-protocol inspection. Image builds are outside this runtime gate.

## Required behavior

### Definition and sequencing

```yaml
# services/shop.yml, beside factory:
pipelines:
  build:
    steps: [shape, work]
    on_question: shape
```

```text
farmy factory pipeline start <name> <pipeline> --task <file|text>
```

Steps select the service's factory profiles and execute in order. `shape`, `work` and `build` are
examples, not built-in names. Task text/file selection follows the existing factory command contract.
Status, show, list and the TUI show pipelines and their current step, including a step blocked on
review or a question. A later step starts only when its predecessor's completion/review policy permits
it; human approval cannot be supplied by an agent or inferred from a successful gate.

### Draft publication, approval and revision

A run ending `awaiting_review` pushes its branch immediately as a draft, before approval. Show, the
TUI and its notification display a compare link derived from the repository URL. Support GitHub,
GitLab and Forgejo/Gitea comparison formats; an unknown host displays the branch name. A workbench
without a remote retains useful local review under the contract settled above.

`farmy factory approve <id>` records the exact commit approved. `--from` and the next pipeline step
start from that recorded commit, never from the branch's current head. This applies whether a known
run is selected by ID or by its branch name; a branch alias cannot bypass review. Subsequent branch
movement does not confer approval on another commit. The starting commit remains the new run's
protection baseline, and the preceding gate evidence still reaches its prompt.

`farmy factory revise <id> <text|file>` reruns the same profile on the same branch, carries the
original task and the supplied feedback in its prompt, and returns to `awaiting_review` after a
successful gate. Its draft is updated for another review. Revision does not start the next step or
reuse approval for changed content. Runs still obey profile writes, protects and hidden paths.

### Questions and reviewed answers

With `on_question: shape`, a worker's `.farmy/question.md` starts that profile with the question as
its task. Existing question capture and permitted-work preservation still apply. The worker waits
for the response; the configured shaper remains subject to its own permissions.

If the shaper answers only in `.farmy/answer.md`, the worker continues with the answer in its prompt.
If it changes anything under its permitted writes, the change goes through the normal shape gate,
draft publication and human review before the worker receives it. An answer file alongside edited
tests does not make the result text-only. The worker must never adopt unreviewed test changes.

A pipeline has a handoff limit, default three. Reaching the agreed boundary stops further handoffs
and ends the pipeline `handoff_limit`. Preserve the question/answer history and the count so a new
controller process cannot restart the budget. The precise counting convention is open above.

### Meaningful red gates

A red_first gate may set `red_pattern`. In addition to the existing successful check, non-zero test
exit and added/changed committed file under writes, the test output must match that pattern. A crash,
load error or a gate that failed to run is not evidence of the intended red. Matching output cannot
replace any other red_first condition. Profile authors choose a pattern that identifies a meaningful
failure in their suite; the option does not establish a universal assertion format.

### Parallel runs and sidecars

Runs of one service may execute concurrently. Each run's gate uses its own copies of the service's
sidecars in a separate Compose project named after the run, with its own data volumes and no published
ports. Gates retain the configured sidecar service names for discovery. The app's sidecars and another
run's sidecars are not joined into this project's gate network.

The run's sidecar resources are removed with that run. Cancelling one run must leave the other run,
its sidecars and its data usable. `factory.concurrency`, default two, caps concurrent runs per service;
ordinary runs, pipeline steps and question handoffs must obey the same cap. Different services have
their own limits. Slot and sidecar lifetime details are open above.

### Notifications

`notify:` in `farmy.yml` configures a webhook URL for ntfy, a Slack-compatible receiver or a plain JSON
POST endpoint. Notify on `awaiting_review`, `question`, `green` and failures. The payload carries the
compare link, or the branch fallback where a compare link cannot be constructed, with enough run and
pipeline identity to locate the work. A review notification follows successful draft publication so
the link is usable. Tests use a local fake receiver; recording this feature sends no external messages.

### Egress terminology and scope

The canonical restrict values become `off | audit | enforce`. Boolean `true` remains accepted as
`enforce`. Existing policy strength remains enforce above audit above off; a service cannot weaken a
stronger workspace policy, and factory agents keep enforced access to their configured API hosts.

Document exactly what the runtime gate covers: HTTP requests and CONNECT tunnels. In audit and
enforce, other protocols have no independent outbound route around the gate. The gate does not
inspect application traffic inside CONNECT. Image builds are outside this gate. This is a small
configuration/documentation change, not a new general-purpose protocol firewall.

## Tests through the fake

Extend the existing fake Docker, real Git in fake volumes and played agent actions. Farmy, not the
fake, decides step transitions, review, approved commits, answers, gate verdicts and concurrency.
Observe pushes at a local remote, prompt contents, commit ancestry, public status, generated Compose
projects and network/volume operations. Notification tests capture actual HTTP requests at a fake
receiver and inspect their payloads.

The sidecar concurrency test must overlap two live runs and exercise their separate database state,
not just compare project-name strings. Use deterministic barriers to keep both gates active, write
distinct data through the database sidecar interface, cancel one run and demonstrate that the other
still reads only its own data and can finish. Keep the production and other run's resources outside
the cancelled run's cleanup.

## Scenario list

- Starting a named pipeline runs its configured profiles in order and carries the task from literal text or a file.
- Unknown pipelines or step profiles are refused by name before an agent starts.
- Status, list, show and the TUI's public data expose the pipeline, current step and active or waiting run.
- A successful review-required shape gate immediately pushes its draft and stops before the worker starts.
- GitHub HTTPS and SSH repository URLs produce the expected review comparison link.
- GitLab and configured self-hosted GitLab repository URLs produce the expected review comparison link.
- Forgejo and Gitea repository URLs produce the expected review comparison link.
- An unknown forge or a repository without a remote gives the branch fallback under the agreed publication rules.
- Show, TUI data and the awaiting_review notification expose the same comparison target after the draft is pushed.
- A failed draft push reports the publication failure without advancing to the next profile or claiming a usable published review.
- Approval records the exact gated commit and starts the next step from that commit.
- Moving a branch after approval does not change the source commit selected by --from using either run ID or known branch name.
- Moving a branch after approval does not change the commit inherited by the next pipeline step.
- An unapproved draft cannot be used through --from by run ID or by its branch name.
- Repeating an approval or resuming the controller does not launch the same next step twice.
- Revision reruns the same profile on the same branch with text feedback and returns a new draft to review.
- Revision reads feedback from a file and preserves the original task in the prompt.
- A revision's changed commit is not covered by an earlier approval and the worker stays blocked until fresh approval.
- A worker question starts the configured on_question profile with the question as its task.
- A shaper answer containing only answer.md resumes the worker with the answer and its previous permitted work intact.
- An answer accompanied by a permitted test change waits for its gate, draft publication and human approval before the worker resumes.
- Revising that answer's test change still withholds it from the worker until the revised commit is approved.
- The question and answer control files follow the agreed capture and cleanup contract and do not recur as stale questions.
- The pipeline stops as handoff_limit at the default boundary without starting an extra shaper run.
- An explicit handoff limit and a resumed controller preserve the agreed pipeline-wide count.
- A red_first gate with a matching meaningful failure pattern passes only when all its other conditions hold.
- A non-zero test that lacks red_pattern's match does not count as a successful red_first gate.
- A crash, load error or gate launch failure does not count as meaningful red under the agreed failure classification.
- An invalid red_pattern is refused before execution, while omitting it preserves existing red_first behavior.
- Two simultaneous runs of one service use distinct Compose projects, independent database volumes and no published sidecar ports.
- Both live gates access their database by the configured sidecar name and cannot observe the other run's data.
- Cancelling one of those runs removes only its sidecars and volumes while the other gate remains usable and completes.
- Run cleanup preserves the developer's service sidecars and their data.
- The default concurrency cap allows two runs of a service and handles a third according to the agreed queue or refusal policy.
- An explicit concurrency cap applies to direct runs, pipeline steps and question handoffs without consuming another service's slots.
- A gate with network none starts no sidecars and preserves its existing isolation.
- Awaiting review, question, green and failure transitions deliver the agreed webhook event with its comparison link or branch fallback.
- Ntfy, Slack-compatible and plain JSON notifications use their agreed request formats against a fake receiver.
- Failed notification delivery follows the agreed retry/reporting policy without silently losing the run's recorded outcome.
- Off, audit and enforce are accepted at the supported global and service restrict locations and true remains an enforce alias.
- Stronger egress policy wins, audit and enforce retain no direct route out, and factory agents remain enforced.
- Egress documentation describes HTTP and CONNECT coverage, the lack of an independent route for other protocols, and image builds outside the gate.
- The full pipeline shapes a failing test, pushes a draft, revises it, approves an exact commit, starts work from that commit, routes a worker question to a text-only shape answer, and continues to green.

Contract-dependent details are settled before the tests are written. The complete pipeline scenario
must inspect commits and prompts as well as final status, so a green result cannot conceal an
unreviewed test or a continuation from the wrong source.

## Existing contracts affected

`test/farmy/factory_profiles_test.rb` has explicit no-push assertions for checked shape work and for
a green gate requiring review. Those become draft-push assertions. Approval still authorizes the
exact gated content, but publication moves before it. The unapproved --from tests keep their refusal
and no-new-agent expectations while allowing the draft that already exists. Prune still preserves
material needed for review or an answer; its old publication rationale needs updating.

The shaper-and-worker contracts and `FORMATS.md` currently refuse a known run branch that advanced
after approval. This record replaces that behavior with starting from the immutable approved commit.
It does not make an unreviewed branch tip eligible for use.

`test/farmy/factory_test.rb` currently expects a gate to reach the developer's existing `shop-pg`
container by the alias `postgres`. Change that expectation to its run's own sidecar instance and
retain alias discovery. The network-none case, gate isolation and independent commit export keep
their meaning. Existing cancel/prune tests gain resource-ownership coverage for the new projects.

`test/farmy/audit_egress_test.rb`, `test/farmy/egress_control_test.rb` and the egress portions of
`FORMATS.md` use boolean input and strict/unrestricted terminology. Add canonical named inputs and
change public mode expectations only after the compatibility decision above. Proxy behavior and
the stronger-policy rule are not relaxed.

## Worker handoff

After confirmation, the shaper reads `TESTING.md`, writes the new and changed scenarios, runs them
through the fake and checks that each failure describes the missing behavior without depending on
worker source. Record the settled pipeline/run schema, immutable approval fields, answer/revise
contracts, handoff accounting, sidecar lifecycle, concurrency policy, notification payload and egress
compatibility in `FORMATS.md`. Commit tests and contracts separately from implementation on
`farmy-workbench`.

The worker uses `bin/verify` output and `FORMATS.md` to implement the behavior, checks the TUI rendering
on its side and passes the full suite. No automatic human approval, merge, forge pull-request API or
protocol inspection beyond the stated gate scope is included. Existing standalone profiles and
manual answers remain supported alongside pipelines.
