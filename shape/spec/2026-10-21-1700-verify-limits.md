# Verify limits: what one agent's verifies may cost farmy

The owner, 2026-10-21, after a read-only review of the worker's on-demand verify (commit 42c9273, record
2026-10-21-1332). The review was done by a work-side helper that read the code and never this folder; its findings
shaped these decisions. It found no breach of the hidden folder. It did find three ways an agent can make the run's
controller run out of memory:
- a verify's output had no limit;
- waiting calls had no limit, and each was held in memory with its words;
- output from the verify container before its command started was held without limit.

It also found that a newline in an argument was written raw into the record's `command:` header line, so an
argument could forge header lines (an `exit: 0`, an early end of the header).

## Decided (the owner)

1. **Output cap.** A verify's stdout and stderr together are capped at 4 MiB. At the cap the command is stopped;
   the agent gets what was streamed so far, then one line saying the output exceeded 4 MiB and the verify was
   stopped, and exit 125, as a "could not run". The record keeps the same truncated output and the reason. The cap
   is a constant named in FORMATS.md, not a config key.
2. **Queue limit.** At most 4 waiting calls per run. A fifth fails at once with exit 125 and a line saying the
   queue is full, and leaves nothing behind. A call is read into memory only when its turn comes; a waiting call
   costs only its directory entry.
3. **Before the command.** Output that arrives before the command starts is capped at 64 KiB. At the cap the
   verify ends as "could not run" with a line saying so, and nothing of that output is held beyond the cap.
4. **Record header.** The command line and every argument are written so that a newline or control character in
   an argument cannot start a new header line. The way it is done is chosen here, and stated in FORMATS.md.

## Chosen here (the owner may overrule any of these)

- **Where each cap falls.** The first 4 MiB (4,194,304 bytes) pass and the first byte beyond stops the command, so
  a command that prints exactly 4 MiB is not stopped. The same holds for 64 KiB (65,536 bytes) before the command.
  The output cap counts only the command's own output; what comes before the command has its own cap.
- **The lines**, each on stderr on a line of its own:
  - `farmy-verify: could not run: the output exceeded 4 MiB, so the verify was stopped`
  - `farmy-verify: could not run: the verify queue is full (4 calls are waiting)`
  - `farmy-verify: could not run: the verify container printed more than 64 KiB before the command started`
- **The constants:** `VERIFY_OUTPUT_CAP`, `VERIFY_QUEUE_LIMIT`, `VERIFY_PREPARE_OUTPUT_CAP`.
- **"Waiting" excludes the running call.** One runs, four wait, and the next call is refused.
- **A refused call is not a verify.** It gets no number `k`, no record file, and isn't counted. A flood of refused
  calls then costs no disk.
- **"Leaves nothing behind" means anywhere the agent's container can write,** not only the request folder, whose
  name and place are the worker's.
- **The record header:** `command` and `reason` are JSON strings, as `args` is already a JSON array, so no header
  value spans a line. `reason` is included because a "could not run" reason can quote git's output, which can name
  files the agent made. The earlier record's example showed both as plain text; FORMATS.md now shows them quoted.

## How the tests play it

The fake learned three things:
- **Big output.** An agent's command line that prints more than 256 KiB keeps its output in files, so the journal
  stays small and a failure shows only the size and both ends of the output.
- **`list_writable`.** This step lists every entry the agent's container can see under a mount it can write. A
  test compares the listing just before a call with the one just after it.
- **`verify_containers_print_first`.** Every verify container prints that many bytes before it runs its process.
  This stands in for output that comes before a verify's command starts: in a real container that would be its
  preparation or `gate_setup` code writing to the container's own output. If the container is stopped meanwhile,
  its process never runs.

Two throwaway probes (deleted afterwards) checked the listing:
- It sees a file put in the agent's writable bind, and leaves out the read-only one.
- Under the current program, the four waiting calls and the fifth all fall well inside the first verify's 5 s.

## Not tested

These are stated in FORMATS.md as contracts:
- A waiting call costs only its directory entry, and farmy never holds more than a cap in memory. Memory is not
  visible from outside, and the fake does not measure the controller. The tests show what the agent and the record
  get.
- A command that prints exactly 4 MiB is not stopped, and the same for 64 KiB. The owner asked for one test per
  point.
- A refused call leaves no record and no count.

## Left out

The review's other findings:
- The snapshot and compose steps cannot be interrupted, which can stall the end of an iteration.
- `gate_setup` code can print a forged marker.
- Non-UTF-8 words are changed silently.
- The 1 MiB request limit cannot actually be reached.
- The request folder is open to every host account.
- The args are appended after the line's last character.

The gate keeps its own unbounded output, as the first record kept the gate unchanged.

## Tests altered

None. The kit's `verify_record` now decodes `command` and `reason` when they are JSON strings. `assert_agent_got`
and `refute_agent_got` read a big output from its file. No existing test asserted the old plain form of
`command` or `reason`; the one that reads `reason` checks that it includes "stopped".

## Scenario list

FactoryVerifyLimitsTest (factory_verify_limits_test.rb):
1. A verify whose output passes 4 MiB is stopped there: the agent and the record get the first 4 MiB as it came
   and the reason, with exit 125.
2. With one verify running and four calls waiting, a fifth waiting call is refused at once with exit 125, saying
   the queue is full, and leaves nothing behind.
3. A verify container that prints more than 64 KiB before its command starts ends as could not run, saying so,
   and the agent gets no more than 64 KiB of it.
4. A newline or control character in an argument cannot start a header line of the verify's record.
