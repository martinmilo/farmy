# 2026-10-15 10:00 — The factory loop

The reason farmy exists: an agent works on a repository in a loop until a separate test run passes,
and nothing the agent says counts as success. Reviewer 2's acceptance table (run workspace, iteration
loop, protected gate, retry and termination, isolation, publishing, mission control) is the skeleton;
the owner fixed the design (this record's sections 1 to 7). Where the design left a choice, the choice
made here is stated, and listed again under "Open questions" for the owner.

## 1. Definition

A service opts in with `factory:` in its definition:

```yaml
factory:
  base: main              # the branch runs start from
  agent: claude           # a catalogue agent (or one of farmy.yml's), in api-key mode or with a token_env
  writes: [src/]          # paths the agent may change; default: the whole repository
  protects: [test/]       # paths whose changes by the agent are reverted before the gate runs; default: none
  hidden: []              # protected folders not even visible in the agent's container
  test: test              # a name from commands:, run from the repository root
  max_iterations: 5       # default 5
  iteration_timeout: 30m  # default 30m
```

The default fits any repository: the agent sees everything, the protected paths are reverted, the gate
decides. farmy knows no folder names. `factory.agent` puts that agent into the service's image (as if
the definition said `agents: {<agent>: api-key}`, or its token mode). Refused, each naming what to fix:
`test` not under `commands:`; an agent unknown to the catalogue and to `farmy.yml`; an agent with neither
a route to its `api.upstream` nor a `token_env`; a `hidden` entry that is not also under `protects`
(hidden is a stronger protects, so it is added there, not refused: a hidden path is always protected).

## 2. The run workspace

`farmy factory start <name> --task <file or text>` (a path to a file in the containers folder is read;
anything else is the task's text) creates run `<id>` (`<yyyymmdd>-<hhmmss>-<4 hex>`, UTC) and prints it.

- **The service must be running** (refused otherwise, naming `farmy start <name>`): the run clones its
  checkout and uses its keys container for git's credentials.
- **The run volume** `<name>-run-<id>`: a short-lived **git container** (the service's image, entrypoint
  `sh`, labels below) clones the checkout volume `<name>-src` locally into it (no network), points
  `origin` at the service's clone URL (as farmy rewrites it for an SSH route), fetches, checks out the
  remote's `base` and creates the branch `farmy/<name>/<id>` there. The developer's checkout is never
  written. A checkout without a remote (a workbench whose `/workspace` is a repository of its own) runs
  from its local `base`, without fetch or push.
- **Who holds what.** Only git containers get the service's git credentials: they join the service's
  compose network, get its `DEV_GIT_ROUTES` rewrites (as `git -c url.….insteadOf=…`) and, with an SSH
  route, its agent socket (`<name>-keys-agent`, `SSH_AUTH_SOCK`). Git runs there with
  `-c core.hooksPath=/dev/null -c core.fsmonitor=false`.
- **The run's own broker**, `<name>-run-<id>-keys` (network alias `keys` on the network
  `<name>-run-<id>`), holds the agent's API route and nothing else, loaded with values from the holder
  (record 0900) or the provider; a run needs no prompt. In token mode the agent's `token_env` secret goes
  into the agent container's environment instead.
- **The agent's container** (the service's image, entrypoint `sh`, user `dev`): the run volume at
  `/workspace`, `/workspace/.git` covered by an empty read-only tmpfs (no history, no hooks, no
  config to plant), each `hidden` folder covered the same way; on the run network only; no
  `SSH_AUTH_SOCK`, no `<name>-keys-agent`, no `DEV_GIT_ROUTES`, no `farmy-shared`, no knowledge MCP
  (`FARMY_MCP_URL`), the logins on nothing shared (as `shared_logins: false`). A subscription login is
  never mounted into a run. The definition's `mounts:` (dependency caches) are mounted as the service
  mounts them.
- **Labels** on every run container: `farmy.run=<id>`, `farmy.service=<name>`, `farmy.role=git|agent|test`,
  `farmy.iteration=<i>` (git and test, agent). Names: `<name>-run-<id>-git-<n>`,
  `<name>-run-<id>-agent-<i>`, `<name>-run-<id>-test-<i>`.

## 3. Iteration

For `i` in 1..`max_iterations`:

1. **The agent** runs headlessly in a new agent container, `docker run --rm -i`, its command
   `timeout <iteration_timeout in s> <the catalogue's headless command>`; the prompt goes on its stdin
   or as the last argument, as the entry's `headless.prompt` says. The prompt is farmy's template
   (`factory-prompt.md` in farmy's folder), or `factory/prompt.md` in the containers folder when there is
   one, with `{{TASK}}`, `{{ITERATION}}` (`<i> of <max>`) and `{{TEST_OUTPUT}}` (the last 200 lines of the
   previous gate's output, with its exit code; for the first iteration a sentence saying no test has run
   yet) filled in. Its output is kept as `iteration-<i>.agent.log`.
2. **The commit**, in a git container: revert everything under `protects` (and `hidden`) to the run's
   base commit, removing what the agent added there, ignored files included; stage what changed under
   `writes` (default everything); commit as `farmy: iteration <i>` on the run branch when anything is
   staged; then reset the working tree to that commit (changes outside `writes` are dropped, untracked
   files removed, ignored files outside `protects` kept), so the gate tests exactly the commit.
3. **The gate**: a new test container (the service's image, entrypoint `sh`) runs the test command from
   the repository root, the run volume mounted read-only at `/workspace`, a tmpfs at `/scratch` (`HOME`
   and `TMPDIR` point there), no network. Its exit code is the verdict; its output is kept as
   `iteration-<i>.test.log`. Exit 0 ends the run green; otherwise the next iteration.

The agent's exit code and words decide nothing, with one exception (agent_failed, below).

## 4. Terminal states

Persisted in the run's state, each final:

| State | When |
|---|---|
| `green` | a gate exited 0 |
| `max_iterations` | the last iteration's gate was red |
| `timeout` | an iteration's agent ran past `iteration_timeout` (stopped), and that iteration's gate was red |
| `agent_failed` | the agent exited non-zero and nothing was committed (the gate is not run) |
| `test_failed_to_run` | the test container could not start (Docker refused it) |
| `cancelled` | `farmy factory cancel <id>` |
| `interrupted` | the controller is gone and the run was in progress |

Only `green` pushes the run branch to the remote (`git push origin farmy/<name>/<id>` in a git container).
Nothing merges. The run volume stays after the run (for `show`, `log` and a look inside); the run's broker
and network are removed.

## 5. Protection

The git container reverts the agent's changes under `protects` and commits only what remains before every
gate; the test container is new each iteration, the run volume read-only in it but for the scratch tmpfs,
and its exit code is the only verdict. The tests: an agent that edits a test file sees that edit gone at
the gate; an agent that prints "tests pass" with a red suite does not produce green; a hidden folder is
covered in the agent's container and its edits there reach no commit; the agent's container has no git
history, no agent socket and no `farmy-shared`.

## 6. Mission control

A run lives in `.work/<name>/runs/<id>/`: `state.json` (id, service, task, base commit, branch, phase,
iteration, max_iterations, result, started, ended, commits per iteration, verdicts per iteration, the
controller's pid) and `iteration-<i>.agent.log`, `iteration-<i>.test.log`. Phases: `cloning`, `agent`,
`commit`, `gate`, `pushing`, `done`.

- **The controller.** `farmy factory start` starts the controller, `farmy factory run <id>`, detached (its
  own session, standard streams closed), and returns; with `--wait` it runs the controller itself and exits
  0 for green, 1 for any other end. Any farmy command that reads runs (`factory list/show`, `status`) marks
  a run whose phase is not `done` and whose controller is gone `interrupted`.
- `farmy factory list [<name>]`: one line per run, `<id>  <service>  <result or phase>  <i>/<max>  <branch>`.
- `farmy factory show <id>`: the state as lines (service, task's first line, base, branch, result or phase,
  iteration, each iteration's commit and verdict) and the last gate's output.
- `farmy factory log <id> [<iteration>]`: that iteration's agent log and test log (default: the last).
- `farmy factory cancel <id>`: stops the controller and the run's containers, removes its broker and
  network, marks the run `cancelled`.
- `status --json`: each service gets `runs`, a list of `{"id", "phase", "iteration", "max_iterations",
  "result", "branch", "started", "ended"}`, oldest first (`[]` without runs). The TUI lists them under
  their service (not under test).

## 7. The catalogue's `headless` field

`headless: {command: <the command line without the prompt>, prompt: stdin | argument}`, verified per vendor
as the rest of the catalogue was, a URL above each entry; null for a vendor that has none. An agent of your
own may give it in `farmy.yml`. An agent without `headless` cannot be `factory.agent` (refused, naming the
field).

## Open questions (with the choice made here)

1. **Hidden: masking or subpaths.** A hidden folder is covered by an empty read-only tmpfs in the agent's
   container; the agent runs without the capabilities to unmount it. A volume-subpath layout (mounting every
   other top-level entry separately, Docker 26 and later) is stricter but loses what the agent writes at the
   repository root. Hidden entries must be folders.
2. **`.git` in the agent's container** is covered too: the git container would otherwise run the hooks and
   config the agent left there, with the agent socket in reach. The agent has no history to read.
3. **Changes outside `writes`** are dropped before the gate, so the gate tests exactly the commit. Ignored
   files survive (dependency caches), except under `protects`; an agent could still leave an ignored file
   that changes the tests' behaviour.
4. **A read-only tree at the gate** breaks suites that write into it (Rails' `log/`, `tmp/`). Options: copy
   the tree into the scratch tmpfs (`factory.test_copy: true`), or named writable paths.
5. **Sidecars.** A run has none: the agent and test containers do not join the service's network (its
   broker holds the git route). A suite that needs Postgres does not run green yet. Option: a run starts the
   fragment's services in a compose project of its own.
6. **`timeout`** ends the run after that iteration's gate (red); a hanging agent is taken to hang again.
7. **The gate has no network.** A suite that downloads at test time fails.
8. **Dependencies.** The definition's `mounts:` are shared with the developer's service (read-write in the
   agent's container, read-only at the gate); the `setup` command is not run in a run.
9. **Concurrency.** Several runs of one service may run at once, each with its own volume; no limit yet.
10. **Run volumes** are kept; nothing removes them yet (`farmy destroy <name>` removes the service's own
    volumes only). A `farmy factory clean` is for later.
11. **Egress.** The agent's container reaches the internet directly; egress control is a later record.
12. **The `headless` values** are what the vendors document on 2026-10-15; the bypass flags each vendor
    names for unattended runs are in the command (the container is the sandbox).

## Tests

The fake docker learns the factory: a `docker run` labelled `farmy.role=git` or `test` runs its command for
real, on a folder per volume (mount targets in the command replaced by the folders; a read-only mount made
read-only for the run; a tmpfs a fresh folder; `timeout <s>` honoured), so git and the test command act on
real files; one labelled `agent` plays what the test said the agent does (`agent_plays`: files it writes,
words it prints, its exit code, an idle time), its writes landing nowhere under a covered path; an app
container whose `REPO` is a `file://` URL gets a real clone in its checkout volume's folder; `fail_role`
makes Docker refuse a role's container. Every `docker run` is kept with its labels, mounts, tmpfs, env and
stdin.
