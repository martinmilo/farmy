# Shipping 0.2.0

The owner, 2026-10-23: the release after 0.1.1 is 0.2.0, not 0.1.2. It brings a new profile key (`verify`), a
new program in the agent's container (`farmy-verify`), new record files (`iteration-<i>.verify-<k>.log`) and
three new contract constants in FORMATS.md (`VERIFY_OUTPUT_CAP`, `VERIFY_QUEUE_LIMIT`,
`VERIFY_PREPARE_OUTPUT_CAP`). That is a contract change, and anyone reading the tag should see it. 0.1.1
shipped features under a patch number. The owner called that a reason to number this one right, not a
precedent to repeat.

## Decided

- `Distribution::SHIPPED` is `0.2.0` (record 2026-10-19-1310: at a release, only `SHIPPED` changes for the
  tests that mean the shipped version).
- Record 1310 kept literals for tests about an older (`0.0.9`) or a newer (`0.2.0`) release. A newer release
  must now be one after 0.2.0, so these tests use `0.3.0` instead. The two that also need a still later
  release as latest use `0.4.0` for it, where they had `0.3.0`. Nothing else in them changes.
- Tests about an older release, and publication's own scratch repositories (their own `VERSION`, 0.1.0),
  are untouched.

## Tests altered (the version only; what each one checks is unchanged)

DistributionTest:
- a mismatched folder pin refuses the binary before any service starts and names the fix
- a quoted folder pin mismatch is refused by the shim before control starts
- version remains available while the folder pin mismatches
- a toolbox built by 0.3.0 is not marked older than the shipped 0.2.0 (was: built by 0.2.0 … the shipped
  0.1.1). The old list `[SHIPPED, "0.2.0"]` would have named the same test twice.
- a shim older than the running control image warns with both versions and update (through the kit's
  `newer_running_control`)
- farmy.yml and services/shop.yml: format 2 refuses before start and names a published version that reads it
- latest metadata that still cannot read the requested format does not invent a capable version

InstallationTest:
- installation without a version resolves the stable latest control label
- an unpinned update pulls every newest release image and replaces the installed shim
- an explicit update target overrides latest and fixes an existing folder mismatch (0.3.0 pinned, 0.4.0
  latest)
- update without a target respects an exact folder pin instead of latest (0.3.0 pinned, 0.4.0 latest)
- a failed helper-image update preserves the installed shim and all running containers
- a failed shim extraction preserves the installed executable

ReleaseInstallerTest:
- the release's installer, run without --to, installs the release it came from even when a newer one is
  latest
- the release's installer with --to installs that version

ReleaseTest:
- release version 0.3.0 is refused because it is invalid or differs from repository VERSION (was 0.2.0,
  which is now the repository's VERSION)

PublishingDefaultsTest:
- update without a registry override obtains all four roles from the configured GHCR namespace

## Left as it is

The newer-release literals will need the same move again at a release that ships 0.3.0. Naming "a newer
release" once, as `SHIPPED` names the shipped one, would end that. It is left for the owner to decide.
