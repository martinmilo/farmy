# Distribution, audit egress and readable logs

The owner verified enforced egress on a real machine: an allowed destination worked
through the gate, an unlisted destination was denied and logged, bypassing the proxy
could neither resolve nor connect, and a restricted factory run passed its gate.
This is external integration evidence for the preceding egress-control record.

The next complete shaper-and-worker cycle stays on `farmy-workbench`: this record
with open questions and scenarios, acceptance tests, then the worker implementation,
committed separately. The owner requested the complete cycle and supplied the main
scenarios. Neither agent approves its own work.

## Decisions

Farmy has one repository version, initially `0.1.0`. `farmy --version` prints it
with the build hash. Every image farmy creates or publishes carries `farmy.version`
and `farmy.hash`; pulled farmy images carry the same release metadata.

`bin/release <version>` uses Docker buildx to build and push control, keys, knowledge
and gate images for `linux/amd64` and `linux/arm64`. `FARMY_REGISTRY` selects the
registry; none is hard-coded. Documentation gives GitHub and self-hosted Forgejo
examples, and CI is an example file, not a prerequisite.

The POSIX host shim pulls the versioned control image by default. `FARMY_BUILD=1`
or a failed pull selects a local build, and output names which path was taken. A
POSIX install script puts only this shim on PATH, requires Docker rather than a
host compiler or clone, and supports installation into a temporary bin directory.
`farmy update` fetches the newest release images and replaces the shim;
`farmy update --to <version>` selects a specific version. A `farmy:` pin in a
containers folder refuses mismatched execution and gives the corrective command.

Status identifies a toolbox built by an older farmy and gives `farmy rebuild <name>`.
The shim warns when it is older than the selected control image. Definitions and
`farmy.yml` accept `format: 1`; absent format means 1. A newer format is refused
with the version of farmy required to read it.

`farmy egress log` becomes readable lines containing time, service, container,
host:port and decision. `--json` preserves the machine-readable log interface.

Global and per-service `egress.restrict: audit` keep the internal-only topology and
the gate path, but allow every host and log each new destination once per container.
Audit events appear in egress log. Factory agents ignore audit and remain restricted
to their own catalogue API hosts. Documentation recommends restriction for factory
runs and audit for interactive containers whose agents use WebFetch.

## Open questions

- What registry artifact identifies the newest stable version and supplies the
  standalone shim, so installation needs no HTTP client, Git or host language?
- Where does a standalone shim obtain source for local fallback after a pull fails?
  A configurable source URL consumed by Docker can keep the host free of a clone.
- Is the folder pin an exact version, or does `0.x` mean a supported version range?
- Which restriction wins when global and service values differ between true,
  audit and false? The existing rule forbids a service opting out of global true.
- How is the minimum reader for a future, unknown format discovered without
  pretending to know a release that does not exist?
- What timestamps and decision values are exposed in readable and JSON audit logs,
  and do reloads preserve the set of destinations already observed?

## Changed meaning and exclusions

The existing shim tests that require building locally by default will change to
pull-first behavior; explicit development builds retain their caching checks.
Existing egress log assertions will request JSON when testing structured data.
Existing unrestricted containers, strict factory policy, credential isolation,
gate failures and HTTP/TLS behavior keep their meaning. This work supplies release
automation but does not publish a release or choose the owner's registry.

## Scenarios

- The command and TUI report repository version 0.1.0 and the same build hash.
- Farmy-built images carry version and hash labels, including service toolboxes.
- A shim with a published control image pulls it and reports that choice without a local build.
- A failed control pull falls back to a build and reports both the failure and fallback.
- FARMY_BUILD=1 selects the local build without pulling a control image.
- An installed standalone shim runs without a source checkout or host development tools.
- Installation into a selected bin directory leaves only an executable POSIX shim there.
- Updating pulls all release images and atomically replaces the shim with the selected version.
- An explicit update target selects that exact release; a failed update leaves the installed shim usable.
- A folder pin accepts its version, refuses a mismatch and names the update command that fixes it.
- Status reports an older toolbox version and its service-specific rebuild command.
- A shim older than the control image emits an actionable warning.
- Explicit format 1 and an absent format are accepted in both configuration file kinds.
- A newer format is refused before containers change, with the required farmy version named.
- Release records both architectures and all four versioned tags in a fake buildx, using the supplied registry.
- Release refuses invalid versions or a missing registry before publishing anything.
- A real buildx can build one image for both supported architectures when available.
- Egress log presents readable timestamps, identity, destination and decisions while --json retains structured events.
- Audit permits unlisted hosts only through the gate and records a destination once per container.
- Different ports and containers have separate audit observations, which survive a live policy reload.
- Global and service audit settings follow a documented precedence without weakening strict factory policy.
- An audit-enabled factory still denies non-API destinations and retains its strict denial logs.
