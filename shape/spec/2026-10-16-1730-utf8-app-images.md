# App images run with LANG=C.UTF-8

After a container restart this machine had LANG set to a locale that was not installed, and Ruby
fell back to US-ASCII; a test fake crashed on a "→" in a JSON file. App images have the same
exposure: Debian slim images carry only the C and C.UTF-8 locales, so a LANG naming any other
locale, or none at all, leaves tools in ASCII.

## Decided (the owner, 2026-10-16)

farmy's toolbox layer sets `LANG=C.UTF-8` in every app image, whatever the base image. A user's
LANG must never leave the tools in an app image in ASCII. The toolbox integration test checks it in
a real image (`locale charmap` answers UTF-8).

Also accepted the same day, for record 2026-10-16-1630: the broker runs its ssh-agent with
PR_SET_NO_NEW_PRIVS, because a setgid ssh-agent (Debian) otherwise drops the parent-death signal.

## Scenarios

- Every app image runs with LANG=C.UTF-8, set in farmy's toolbox layer (fake Docker: an ENV after
  the last FROM of the toolbox Dockerfile).
- A real linux arm64/amd64 app image executes the catalogue's pinned nvim and rg versions under
  LANG=C.UTF-8 (integration; skips without a real Docker daemon). This renames the two existing
  ToolboxArchitectureIntegrationTest tests.
